React é a biblioteca que mais aparece nas entrevistas de full-stack e a que produz respostas mais decoradas: toda a gente sabe dizer «virtual DOM» e quase ninguém consegue explicar porque é que um setInterval dentro de um useEffect conta sempre até um. Este capítulo é para quem tem base de backend: o modelo mental de UI como função do estado, o que acontece entre chamar setState e o ecrã mudar, as regras dos hooks com a razão de cada uma, onde vive o estado e a diferença entre estado de interface e estado de servidor, e o que mudou com o React 19 e os Server Components. Acaba com quatro exercícios de prever a saída, porque é assim que se separa quem percebeu o modelo de quem o memorizou.

41.1 UI = f(estado): render, commit e reconciliação#

Um componente é uma função que recebe props e devolve uma descrição da interface — elementos, que são objectos leves, não nós do DOM. Quando o estado muda, React chama a função outra vez, obtém uma descrição nova, e compara-a com a anterior para calcular o conjunto mínimo de operações no DOM real. As duas fases têm nome e é importante distingui-las: a fase de render chama as funções dos componentes (pura, pode ser interrompida e repetida, e é por isso que o StrictMode a corre duas vezes em desenvolvimento) e a fase de commit aplica as diferenças ao DOM e corre os effects (síncrona, uma vez). Tudo o que é efeito lateral pertence ao commit — useEffect, useLayoutEffect, refs —, e é por isso que escrever numa variável global ou chamar fetch no corpo do componente é um bug e não uma opinião.

A comparação chama-se reconciliação e tem duas regras que explicam quase todos os comportamentos estranhos. Primeira: elementos de tipo diferente na mesma posição destroem a subárvore e criam outra — trocar <div> por <section> perde o estado de tudo o que está dentro. Segunda: numa lista, a key é a identidade do elemento entre renders; com a key certa (o identificador do dado) React move nós e preserva o estado; com o índice como key, remover o primeiro item faz o segundo herdar a instância e o estado do primeiro. O «virtual DOM» não é a razão de React ser rápido — comparar árvores custa — é a razão de o modelo declarativo ser possível sem que o programador gira o DOM à mão.

React
MidMuito frequente
O que acontece entre chamar setState e o ecrã mudar? Explique render, commit e o papel das keys.

Resposta-modelo

setState não muda nada imediatamente: agenda uma actualização. Quando o handler termina — ou quando o scheduler decide, em transições —, React entra na fase de render: chama a função do componente com o estado novo, e recursivamente as dos filhos cujas props mudaram (ou todos os filhos, se não estiverem memoizados), obtendo uma árvore nova de elementos. Esta fase é pura e pode ser interrompida, abandonada ou repetida; é por isso que o corpo de um componente não pode ter efeitos laterais, e é por isso que o StrictMode a executa duas vezes em desenvolvimento para os apanhar.

Depois vem a reconciliação: comparar a árvore nova com a anterior, posição a posição. Mesmo tipo no mesmo sítio — actualiza as props e mantém a instância e o estado. Tipo diferente — destrói a subárvore e monta outra, perdendo o estado. Em listas, a comparação por posição seria errada, e é para isso que existem as keys: identificam o elemento entre renders, para que React saiba que o item que estava na posição 2 é agora o da posição 0 e o mova em vez de reescrever os três. Com o índice como key, a identidade fica presa à posição, e remover ou reordenar mistura estados — inputs com texto trocado é o sintoma clássico.

A fase de commit aplica ao DOM o conjunto mínimo de mutações calculado, de forma síncrona, e só depois corre os effects: primeiro os useLayoutEffect (antes de o browser pintar, para medir ou ajustar layout) e depois os useEffect (depois da pintura). A ordem dentro de uma árvore é filhos antes de pais, e as funções de limpeza do render anterior correm antes dos effects novos.

Duas notas que costumam distinguir: várias actualizações no mesmo handler são agrupadas num único render (batching, automático desde o React 18 mesmo em promessas e timers); e o valor lido de state dentro do handler é o do render em que o handler foi criado — não o «actual» —, porque cada render tem as suas variáveis. É isso que produz as closures obsoletas de que falamos a seguir.

41.2 Hooks por dentro: regras, batching, dependências e closures obsoletas#

Os hooks funcionam por posição: React guarda, por instância de componente, uma lista de células de estado, e a n-ésima chamada a um hook lê a n-ésima célula. É por isso que a regra «só no topo, nunca dentro de if ou ciclos» existe — não é estilo, é a única forma de a n-ésima chamada ser sempre a mesma. A segunda regra, «só em componentes ou noutros hooks», garante que existe uma instância a quem associar a lista. Um hook personalizado é só uma função que chama hooks; não partilha estado entre quem o usa, cada chamada tem as suas células.

Cada render é uma chamada nova à função, com as suas próprias variáveis. Um handler ou um effect criado num render fecha sobre os valores desse render; se for guardado (num setInterval, num listener, num useEffect com []) continua a ver esses valores para sempre — a closure obsoleta. As defesas são três: a forma funcional setX(prev => …) quando o novo valor depende do anterior; declarar a dependência e deixar o effect refazer-se (com limpeza); ou um useRef para o que precisa de ser lido «actual» sem provocar renders. O linter de dependências não é um incómodo a silenciar — é o detector de closures obsoletas, e cada eslint-disable nele é um bug adiado.

SéniorMuito frequente
Porque é que os hooks não podem estar dentro de um if? E o que é uma closure obsoleta — dê um exemplo e a correcção.

Resposta-modelo

Porque os hooks são identificados pela ordem de chamada. React não tem nomes para os estados de um componente — tem uma lista ligada de células, e a primeira chamada a useState lê a primeira célula, a segunda lê a segunda. Se um hook estiver dentro de um if que num render é verdadeiro e noutro falso, a partir daí todas as chamadas seguintes lêem a célula errada: um useState passa a receber o valor de um useRef, e o resultado é um erro que aparece longe do sítio. A regra existe para que a ordem seja idêntica em todos os renders; a condição vai para dentro do hook (um useEffect cujo corpo começa por if (!activo) return), não à volta dele.

Uma closure obsoleta é uma função que captura o estado de um render e é usada depois de esse render ter sido substituído. O exemplo canónico é um contador com useEffect(() => { const id = setInterval(() => setC(c + 1), 1000); return () => clearInterval(id); }, []): o effect corre uma vez, o callback do intervalo capturou c = 0, e cada tick escreve 0 + 1. O contador mostra 1 para sempre, sem erro nenhum na consola — o que o torna traiçoeiro.

Há três correcções, e a escolha diz algo sobre o problema. A forma funcional, setC(prev => prev + 1), é a certa aqui: o novo valor depende do anterior, e a função recebe sempre o estado mais recente independentemente da closure. Declarar [c] nas dependências também funciona, ao custo de destruir e recriar o intervalo a cada segundo — aceitável para um timer, mau para uma ligação WebSocket. E um useRef que se mantém actualizado (ref.current = c no corpo) serve quando um callback de longa duração precisa de ler vários valores actuais sem se refazer; o React 19 formaliza este padrão com useEffectEvent.

A conclusão que dou é sobre o linter: o aviso de dependências em falta é o detector de closures obsoletas. Cada eslint-disable-next-line react-hooks/exhaustive-deps que vejo em code review é uma pergunta — «que valor é que este effect vai ver desactualizado?» — e quase sempre a resposta é «este», e o bug já lá está.

41.3 Estado: onde vive, quem o partilha e a diferença entre estado de UI e de servidor#

A decisão mais importante numa aplicação React não é a biblioteca de estado — é reconhecer que há dois tipos de estado com regras opostas. Estado de interface (que aba está aberta, um formulário a meio, um filtro) pertence à aplicação, é síncrono, e vive o mais perto possível de quem o usa: no componente, elevado ao pai comum quando dois irmãos o partilham, num store leve quando está longe. Estado de servidor (a lista de encomendas, o perfil) pertence a outra máquina; a cópia no cliente é uma cache, com tudo o que isso implica — pode estar velha, precisa de invalidação, deduplicação de pedidos, retries, e reflecte escritas de outros utilizadores. Tratá-lo como estado de UI, copiando respostas para um store e actualizando à mão, é a origem de metade dos bugs de «a lista não actualizou».

Daí a arquitectura que hoje é consenso: TanStack Query (ou SWR, ou o fetch com cache do Next) para estado de servidor, com chaves de consulta, staleTime, invalidação por chave depois de mutações e actualizações optimistas; e para estado de UI global, o mínimo — useState elevado, Context para valores que mudam pouco (tema, utilizador), Zustand ou Redux Toolkit quando há muito estado transversal com transições complexas. Context não é um store: qualquer alteração re-renderiza todos os consumidores, e é por isso que um Context com o estado inteiro da aplicação é o anti-padrão de performance mais comum.

React
SéniorMuito frequente
Redux, Zustand, Context, TanStack Query — como decide onde vive o estado?

Resposta-modelo

Começo por separar o que é estado de servidor do que é estado de interface, porque as ferramentas certas são diferentes e a maioria dos problemas vem de as misturar. Estado de servidor — tudo o que veio de uma API — é uma cache: TanStack Query trata da chave, da expiração, da deduplicação (dois componentes a pedir o mesmo recurso fazem um pedido), dos retries, da invalidação depois de uma mutação, e das actualizações optimistas com reversão. Com isto, oitenta por cento do que costumava estar em Redux desaparece, porque era só código a copiar respostas para um store e a mantê-las sincronizadas à mão.

O que sobra é estado de interface, e aí a regra é proximidade: useState no componente que o usa; elevado ao pai comum quando dois irmãos o partilham; e só quando está genuinamente longe — o carrinho, o utilizador autenticado, preferências — é que sai para um store global. Context serve para valores que mudam raramente (tema, idioma, sessão) e são lidos em muitos sítios; não serve como store, porque qualquer alteração re-renderiza todos os consumidores, sem selecção.

Para um store a sério, escolho pela complexidade das transições. Zustand para a maioria: uma função, selectores que só re-renderizam quem lê o que mudou, sem cerimónia. Redux Toolkit quando há muitas acções que afectam várias fatias de estado de forma coordenada, quando a equipa é grande e beneficia da estrutura, ou quando as DevTools com viagem no tempo compensam — em fluxos complexos de edição, por exemplo. O Redux clássico, com action creators e reducers à mão, já não se justifica.

E há um terceiro tipo que se esquece: estado no URL. Filtros, paginação, a aba seleccionada — se o utilizador quiser partilhar ou recarregar, tem de estar no URL, e o router é o store. A pergunta que faço a cada pedaço de estado é «quem é o dono e quanto tempo vive?», e a resposta escolhe a ferramenta.

41.4 Dados, formulários, Suspense e fronteiras de erro#

Formulários são onde o modelo «controlado» de React custa mais: cada tecla é um setState e um render, e um formulário de cinquenta campos num único estado re-renderiza tudo a cada carácter. As respostas por ordem de simplicidade: campos não controlados com FormData na submissão quando não há validação em tempo real; React Hook Form quando há, porque regista os campos por ref e só re-renderiza o que muda; e validação com um esquema partilhado (zod) que idealmente é gerado do mesmo contrato que o backend usa. O React 19 acrescenta Actions — funções assíncronas ligadas ao <form action> com estado de submissão (useActionState, useFormStatus) e actualizações optimistas (useOptimistic) — que cobrem o caso comum sem biblioteca.

Suspense permite que um componente «suspenda» enquanto os seus dados não estão prontos e que um antepassado mostre um fallback; com use(promise) no React 19 e com as bibliotecas de dados que o suportam, o carregamento deixa de ser um if (loading) em cada componente e passa a ser uma fronteira declarativa. As error boundaries são o equivalente para erros: um componente de classe (ainda não há hook) com componentDidCatch que apanha erros de render dos descendentes e mostra um estado de erro em vez de desmontar a aplicação inteira. A disciplina que se pergunta é onde pôr as fronteiras: uma por região independente da página, não uma global — para que um widget que falha não leve a página com ele.

React
SéniorFrequente
Um componente lança uma excepção durante o render. O que vê o utilizador, e como desenha isso para não acontecer?

Resposta-modelo

Sem tratamento, o utilizador vê uma página em branco: um erro durante o render desmonta a árvore inteira a partir da raiz, porque React não tem forma de saber o que é seguro mostrar. É o comportamento por omissão desde o React 16 e é deliberado — uma UI parcialmente corrompida é pior do que nenhuma. Em desenvolvimento aparece o overlay; em produção, branco e um erro na consola.

A defesa são error boundaries: componentes que apanham erros de render, de lifecycle e de construtores dos descendentes e mostram um fallback. Ainda só existem como classes (static getDerivedStateFromError e componentDidCatch), por isso quase toda a gente usa react-error-boundary, que dá um componente com fallbackRender, onError para reportar ao Sentry e resetKeys para tentar de novo quando algo muda. O que uma boundary não apanha: erros em handlers de eventos (esses são try/catch normal), em código assíncrono fora do render, e no servidor durante SSR.

A decisão de desenho é a granularidade. Uma boundary global evita o ecrã em branco mas não é uma experiência: qualquer widget que falhe leva a página inteira para o estado de erro. Ponho uma por região independente — a lista, o painel lateral, cada widget de um dashboard — para que a falha fique contida e o resto continue a funcionar, com um botão de «tentar de novo» que redefine a região. Combinadas com Suspense, as duas fronteiras desenham-se juntas: cada região tem o seu estado de carregamento e o seu estado de erro, declarados uma vez, em vez de if (loading) e if (error) repetidos em cada componente.

E o que faço para o erro não acontecer em render: dados validados na fronteira (um esquema na resposta da API, tipos gerados do contrato) para que um campo em falta não seja um undefined.nome no meio do JSX; e os effects e handlers com tratamento próprio, porque o render deve ser puro e previsível o suficiente para não lançar.

41.5 React 19 e Next.js: Server Components, Actions e hidratação#

A mudança de modelo do React 19 é que um componente pode correr só no servidor. Um Server Component executa no servidor (ou no build), pode ser async, ler da base de dados ou de um serviço interno com segredos, e o que chega ao browser é o seu resultado serializado — sem o seu JavaScript, sem as suas dependências. Não tem estado nem effects nem handlers de eventos, porque não corre no browser. A interactividade fica nos Client Components, marcados com 'use client', que são os componentes React de sempre: hidratados no browser, com hooks e eventos. A regra de composição é assimétrica — um Server Component pode renderizar Client Components e passar-lhes props serializáveis; um Client Component não pode importar um Server Component (mas pode recebê-lo como children).

As Server Actions fecham o ciclo: funções marcadas com 'use server' que o cliente invoca como se fossem locais (o framework gera o endpoint), ligadas a formulários com action e ao estado de submissão com useActionState. Para um programador de backend, isto é um RPC com tipos partilhados — e é aí que vale a pena dizer o que se ganha e o que se perde: menos JavaScript no cliente e acesso directo a dados, contra acoplamento ao framework, um modelo mental novo de «o que corre onde», e a necessidade de tratar cada action como um endpoint público, com autorização e validação, porque é o que ela é.

SéniorMuito frequente
O que são Server Components e o que mudam em relação ao SSR clássico? Quando é que não os usaria?

Resposta-modelo

SSR clássico renderiza a árvore inteira no servidor para HTML e depois envia todo o JavaScript ao browser para a hidratar — cada componente corre duas vezes, e o bundle é o mesmo de uma SPA. Server Components mudam a unidade: um componente pode ser só de servidor, e nesse caso corre uma vez, no servidor, e o browser recebe o resultado e nunca o seu código. A árvore passa a ser uma mistura — Server Components para o que é conteúdo e dados, Client Components para o que é interactivo — e o JavaScript enviado é apenas o das partes interactivas.

As consequências que interessam a um backend: um Server Component pode ser async e ler directamente da base de dados ou de um serviço interno, com segredos, sem passar por uma API pública; as dependências pesadas usadas só para renderizar (um parser de Markdown, uma biblioteca de datas completa) ficam no servidor; e as Server Actions dão um RPC tipado para mutações a partir de formulários. É um modelo próximo do que sempre fizemos com templates no servidor, com a diferença de que a interactividade se compõe declarativamente onde é precisa.

Não os usaria em três situações. Numa aplicação que é essencialmente interactiva — um editor, um dashboard em tempo real — onde quase tudo seria Client Component e o ganho é marginal contra a complexidade de «o que corre onde». Quando a equipa não controla o servidor de renderização: RSC exige Next.js ou equivalente em produção, e isso é infraestrutura a operar, com cold starts e custo, contra uma SPA que é ficheiros estáticos num CDN. E quando há um backend Spring com uma API bem definida que outros clientes usam: duplicar acesso a dados dentro do frontend cria uma segunda fonte de verdade e uma segunda superfície de autorização, e prefiro que a UI fale com a mesma API que a app móvel.

O ponto de senioridade é tratar Server Actions como o que são: endpoints públicos. Validar entrada e verificar autorização dentro de cada uma, exactamente como num controlador, porque o facto de parecer uma chamada de função local é uma conveniência de sintaxe, não uma fronteira de segurança.

MidFrequente
O que é hidratação? O que provoca um «hydration mismatch» e como o evita?

Resposta-modelo

Hidratação é o processo de o React, no browser, pegar no HTML que o servidor já enviou e «ligar-lhe» os componentes: em vez de criar o DOM, percorre-o, associa cada nó ao elemento correspondente da árvore, e instala os handlers de eventos. O utilizador vê conteúdo antes de o JavaScript chegar (bom para LCP) mas não consegue interagir até a hidratação terminar — a diferença entre «aparece rápido» e «responde rápido», que se vê na métrica de INP e no tempo até interactivo.

Um mismatch acontece quando o que o servidor renderizou e o que o cliente renderizaria no primeiro render são diferentes. React detecta-o, avisa, e no pior caso deita fora o HTML e re-renderiza tudo no cliente — perdendo o benefício do SSR. As causas são sempre uma fonte de não-determinismo: Date.now() ou aleatoriedade no render, texto que depende do fuso horário ou do idioma do browser, acesso a window ou a localStorage durante o render (o servidor não os tem), extensões do browser a alterar o HTML, e HTML inválido (um <div> dentro de um <p>) que o browser corrige de forma diferente do que o servidor gerou.

A prevenção é fazer o primeiro render idêntico nos dois lados e adiar tudo o que é específico do cliente para depois: ler localStorage num useEffect e actualizar o estado (aceitando um segundo render), ou renderizar essa parte só no cliente com um useSyncExternalStore que devolve um valor de servidor diferente, ou com carregamento dinâmico sem SSR. Datas formatam-se com um fuso fixo ou passam do servidor já formatadas. E para os casos inevitáveis e inofensivos — um carimbo temporal — existe suppressHydrationWarning nesse nó, que é uma admissão explícita e localizada, não uma solução geral.

41.6 Performance: quando memoizar e quando não#

Re-renderizar não é caro por si: chamar uma função e comparar objectos leves custa microssegundos. O que é caro é re-renderizar muito — uma lista de mil linhas porque o pai mudou um contador — ou re-renderizar algo que faz trabalho pesado no corpo. Daí a ordem de ataque: primeiro o profiler, para ver o que re-renderiza e quanto custa; depois mover o estado para baixo (um contador que só o botão usa não devia estar no pai da lista) ou passar componentes como children (que não re-renderizam quando o pai muda, porque o elemento é o mesmo); só depois React.memo nos componentes que recebem as mesmas props e são caros, com useMemo/useCallback para que as props sejam de facto as mesmas. Memoizar tudo por precaução custa memória, comparações e legibilidade — e o React Compiler, que aplica memoização automaticamente onde o código segue as regras, é o argumento definitivo para não o fazer à mão.

O resto é o mesmo de qualquer frontend: listas grandes virtualizadas (só se renderiza o que está no ecrã), code splitting por rota com React.lazy e Suspense, e transições (useTransition, useDeferredValue) para que uma actualização cara — filtrar dez mil linhas — não bloqueie a que o utilizador está a fazer, como escrever no campo de pesquisa.

React
SéniorMuito frequente
Uma tabela de dois mil itens fica lenta ao escrever no campo de filtro. Como diagnostica e o que muda?

Resposta-modelo

Primeiro o profiler do React DevTools com «highlight updates» e uma gravação enquanto escrevo: quero saber quantos componentes re-renderizam por tecla e quanto custa cada um. Há dois diagnósticos possíveis e as correcções são diferentes. Se re-renderizam dois mil linhas a cada tecla porque o estado do filtro vive no mesmo componente que a tabela, o problema é de estrutura; se re-renderizam poucos mas cada um faz trabalho pesado (formatar datas, calcular derivados), o problema é de custo por render.

Para a estrutura, a primeira coisa é separar a actualização urgente da cara: o campo de texto tem de responder à tecla imediatamente, a filtragem pode chegar um pouco depois. useDeferredValue no valor do filtro (ou useTransition à volta do setFiltro) faz exactamente isso — o input actualiza já, a tabela recebe o valor adiado e React interrompe o render da tabela se chegar outra tecla. É a solução que mais muda a experiência com menos código.

Depois, a quantidade: dois mil linhas no DOM é demais independentemente de React. Virtualizo a lista com TanStack Virtual ou react-window, que renderiza só as trinta linhas visíveis, e o problema desaparece por construção. Se a filtragem em si for cara, useMemo sobre o resultado com dependência no valor adiado; e as linhas em React.memo com props estáveis, para que uma linha só re-renderize quando o seu item muda — o que exige que os handlers passados sejam estáveis (useCallback) ou, melhor, que a linha receba o id e vá buscar o que precisa a um store com selector.

O que não faço: pôr memo e useCallback em tudo antes de medir. Cada um custa uma comparação por render e torna o código mais difícil de ler; o profiler diz onde compensa, e o React Compiler faz a maior parte disto sozinho no código que segue as regras dos hooks. E se dois mil itens vierem da API, pergunto-me se deviam vir todos: paginar ou filtrar no servidor é a correcção que faz o frontend deixar de precisar de ser esperto.

41.7 Testar React: Testing Library, MSW e o que não testar#

O capítulo anterior fixou a filosofia; aqui ficam as especificidades. Testes de componente com Vitest e Testing Library: renderizar com os providers reais (o QueryClient, o router em memória, o Context de tema) através de um render personalizado, consultar por papel e nome, interagir com userEvent, e esperar com findBy/waitFor pelo que é assíncrono. A rede com MSW: os handlers definem as respostas da API ao nível de HTTP, o código de dados corre a sério, e um teste sobrepõe um handler para simular o erro 500. Hooks personalizados testam-se com renderHook quando têm lógica própria, mas o mais das vezes testam-se através do componente que os usa.

O que não se testa: que useState funciona, a ordem interna dos hooks, o número de renders, classes CSS. Snapshots só para fragmentos pequenos e intencionais. E o tempo — timers e animações — controla-se com vi.useFakeTimers, nunca com esperas reais.

React
MidFrequente
Como testa um componente que faz um pedido HTTP ao montar e mostra uma lista?

Resposta-modelo

Não simulo o módulo de dados nem o fetch: uso MSW para responder ao pedido ao nível de HTTP. Assim o código real — a chamada, o parsing, a biblioteca de cache, o tratamento de erros — corre no teste, e o que substituo é apenas o servidor. O handler por omissão devolve uma lista com dois itens; renderizo o componente com um render personalizado que fornece um QueryClient novo por teste (com retries desligados, senão o teste de erro espera pelos backoffs), e afirmo com await screen.findByRole('row', { name: /encomenda 1/i }) — o findBy espera pelo assíncrono sem sleeps.

Depois cubro os três estados que o utilizador pode ver. Carregamento: logo após o render, existe o indicador com o papel de status ou progressbar. Erro: sobreponho o handler nesse teste com server.use(http.get(url, () => HttpResponse.error())) ou um 500, e espero pela mensagem de erro e pelo botão de tentar de novo. Vazio: lista sem itens mostra o estado vazio e não uma tabela sem linhas. Se houver interacção — filtrar, paginar — faço-a com userEvent e verifico que o pedido seguinte leva os parâmetros certos, inspeccionando o pedido no handler.

O que fica de fora do teste: quantas vezes o componente renderizou, o estado interno da query, e a forma exacta do JSON além do que a UI mostra. E o que fica noutro sítio: a compatibilidade do JSON com o backend real é um teste de contrato — tipos gerados do OpenAPI no CI —, não um teste de componente.

41.8 Prever a saída: quatro exercícios de renders, effects e batching#

Os exercícios seguintes assumem React 18 ou 19 em produção, sem StrictMode — em desenvolvimento com StrictMode, os renders e os effects de montagem correm duas vezes, e a primeira pergunta a fazer ao entrevistador é exactamente essa. Escreva a saída antes de abrir a solução, e para cada linha, o mecanismo.

Exercício 41.1 — Ordem de renders, effects e limpezas entre pai e filho
Prever a saída6 min

Escreva a saída da consola ao montar, e depois ao clicar uma vez no botão.

A sua solução

Solução de referência

A fase de render é de cima para baixo: o pai corre e devolve um elemento <Filho>, e só depois o filho corre. A fase de commit corre os effects de baixo para cima — filhos antes de pais —, porque quando o effect do pai corre, os filhos já estão montados e prontos (é o que permite ao pai medir ou focar um filho).

No clique, ambos re-renderizam (o filho porque recebeu uma prop nova; sem memo re-renderizaria de qualquer forma). Antes de correr os effects novos, React corre as limpezas dos effects cujas dependências mudaram — e a limpeza fecha sobre o render antigo, por isso imprime cleanup filho 0 e não 1. Depois, os effects novos, outra vez filhos primeiro. O effect do pai não teve limpeza porque não devolveu função.

Com StrictMode em desenvolvimento, a montagem imprimiria cada render duas vezes e, depois dos effects de montagem, uma limpeza e uma remontagem simuladas (cleanup filho 0, effect filho 0, effect pai 0) — é deliberado, para apanhar effects sem limpeza correcta. Dizer isto antes de responder é o que mostra que se conhece a ferramenta e não só o resultado.

Exercício 41.2 — O contador que não conta: closure obsoleta
Prever a saída5 min

O que mostra o ecrã ao fim de cinco segundos, e o que aparece na consola? Escreva as três correcções possíveis e diga qual escolheria.

A sua solução

Solução de referência

O ecrã mostra 1 — e fica em 1 para sempre. A consola imprime tick 0 a cada segundo, indefinidamente. O effect correu uma vez, na montagem, e a função do intervalo capturou o c desse render, que é 0. Cada tick executa setC(0 + 1); o primeiro provoca um render com c = 1, e os seguintes são ignorados porque o valor é igual ao actual. O render novo tem o seu próprio c = 1, mas o intervalo continua a ver o antigo: nunca foi recriado, porque as dependências estão vazias. Não há erro nenhum, e é isso que torna este bug caro.

As três correcções, e o critério. Forma funcional: setC(prev => prev + 1) — React passa o estado mais recente à função, independentemente da closure. É a escolha certa aqui, porque o valor novo depende do anterior; o console.log continuaria a imprimir 0, o que mostra que só corrigiu a escrita, não a leitura. Declarar a dependência: [c] — o effect refaz-se a cada mudança, a limpeza cancela o intervalo antigo e cria um novo com o c actual; correcto, ao custo de um intervalo novo por segundo, aceitável para um timer, mau para uma subscrição cara. Ref: um useRef actualizado no corpo (ref.current = c) e lido no intervalo — resolve a leitura para callbacks de longa duração que precisam de vários valores actuais; é o padrão que useEffectEvent formaliza.

Em code review, a pista é o linter: react-hooks/exhaustive-deps avisa que c falta nas dependências. O bug existe porque alguém silenciou ou ignorou esse aviso.

Exercício 41.3 — Batching, valores capturados e a forma funcional
Prever a saída6 min

Partindo de a = 0, escreva tudo o que aparece na consola depois de um clique, pela ordem, e o valor final no ecrã.

A sua solução

Solução de referência

No handler, a é 0 — o valor do render em que o handler foi criado, e continua a ser 0 durante todo o handler, porque setA não muda a variável, agenda uma actualização. As duas chamadas setA(a + 1) são ambas setA(1): a segunda substitui a primeira. O console.log imprime 0. Só quando o handler termina é que React aplica o lote, num único render: render 1. É o batching.

No setTimeout, as duas actualizações são funcionais: cada uma recebe o estado mais recente e soma um, portanto 1 → 2 → 3. Desde o React 18 também são agrupadas fora de handlers de eventos (automatic batching), logo um único render: render 3. O console.log('no timeout', a) imprime 0 — a closure do timeout é a mesma do handler, do render inicial — e corre antes do render, porque o render acontece depois de o callback terminar.

As duas lições que se dizem em voz alta: setState é assíncrono no sentido de «adiado e agrupado», não no sentido de promise; e quando o valor novo depende do anterior, a forma funcional é a única correcta — setA(a + 1) duas vezes soma um, setA(x => x + 1) duas vezes soma dois.

Exercício 41.4 — Keys por índice e o estado que muda de dono
Prever a saída5 min

O utilizador escreve «olá» no input da primeira linha e depois clica em «Remover» nessa mesma linha. Descreva exactamente o que vê, e diga o que muda com key={item.id}.

A sua solução

Solução de referência

Depois de remover a Ana, a lista mostra duas linhas: «Bruno: [olá]» e «Carla: [ ]». O texto que o utilizador escreveu na linha da Ana aparece agora na linha do Bruno. Nenhum erro, nenhum aviso — só um utilizador confuso.

O mecanismo: as keys eram 0, 1, 2. Depois do filter, a lista tem dois elementos com keys 0, 1. Para React, o elemento com key 0 ainda existe — é a mesma instância de Linha, com o seu estado texto = 'olá' —, só que agora recebe a prop etiqueta = 'Bruno'. A instância que foi destruída foi a de key 2, a última. O estado ficou preso à posição, não ao dado. O mesmo acontece com o estado interno de inputs não controlados, com animações e com qualquer effect que dependa da identidade.

Com key={item.id}, a instância de key 'a' é desmontada (com o seu 'olá') e as de 'b' e 'c' mantêm-se, cada uma com o seu estado: «Bruno: [ ]», «Carla: [ ]». A regra que se enuncia: a key é a identidade do dado entre renders; o índice só é aceitável quando a lista não reordena, não remove pelo meio, e as linhas não têm estado — e mesmo aí, se o dado tiver um identificador, usa-se o identificador. Math.random() como key é o oposto do erro: destrói e recria todas as linhas em cada render, e perde estado e desempenho ao mesmo tempo.

41.9 Resumo e checklist#

React avalia-se pelo modelo, não pela API: quem percebe que cada render é uma chamada nova com as suas variáveis prevê os quatro exercícios sem correr nada, e quem decorou os hooks falha o segundo.

  • UI = f(estado). Render é puro e repetível; commit aplica ao DOM e corre effects, filhos antes de pais, limpezas antes dos novos.
  • Reconciliação por tipo e posição; em listas, por key. A key é a identidade do dado — o índice prende o estado à posição.
  • Hooks são identificados pela ordem de chamada: por isso não podem estar em condições. Cada render fecha sobre os seus valores: closures obsoletas corrigem-se com a forma funcional, dependências declaradas ou refs.
  • Batching é automático em todo o lado desde o 18; setX(a + 1) duas vezes soma um, setX(x => x + 1) duas vezes soma dois.
  • Estado de servidor é cache (TanStack Query: chave, stale, invalidação, optimista); estado de UI vive perto de quem o usa; Context não é store; o URL também é estado.
  • Suspense e error boundaries por região, não globais. Erros em handlers não são apanhados por boundaries.
  • Server Components correm só no servidor, sem estado nem eventos; Client Components hidratam. Server Actions são endpoints públicos: validar e autorizar.
  • Hidratação exige o mesmo primeiro render nos dois lados; o que é específico do cliente adia-se para um effect.
  • Medir antes de memoizar. Mover estado para baixo, children, useDeferredValue, virtualizar — e só depois memo onde o profiler aponta.
  • Testar como o utilizador, com MSW ao nível HTTP, os três estados (carregamento, erro, vazio), sem detalhes de implementação.

Checklist de preparação para as 48 horas antes da entrevista:

  • Resolver os exercícios 41.1 a 41.4 no papel e explicar cada linha pelo mecanismo.
  • Perguntar «com ou sem StrictMode?» antes de responder a qualquer «o que imprime».
  • Ter a Tabela 41.1 na cabeça: a pergunta que decide cada hook.
  • Saber explicar estado de servidor contra estado de UI em trinta segundos, com a Listagem 41.2 como exemplo.
  • Dizer o que um Server Component não pode fazer e porque é que uma Server Action é um endpoint.
  • Ter uma história real de um problema de performance em React e o que o profiler mostrou.

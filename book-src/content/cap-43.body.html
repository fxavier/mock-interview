Os três capítulos anteriores são o que qualquer programador de frontend responde; este é o que só um full-stack responde bem, e é onde um Java sénior ganha a entrevista. O contrato entre a SPA e a API Spring — como se gera, como evolui sem partir o browser que tem a versão antiga em cache, como os erros chegam ao utilizador. A autenticação, que é o sítio onde as decisões do frontend e do backend se tocam de forma mais perigosa. CORS como decisão de arquitectura e não como configuração. Tempo real e listas grandes. E a parte operacional: quem constrói, quem serve, como se liga um erro visto pelo utilizador ao registo do servidor que o causou.

43.1 O contrato: OpenAPI, tipos gerados e erros que a UI consegue mostrar#

O contrato é o openapi.json que o springdoc-openapi gera a partir dos controladores, e a decisão que muda tudo é quem é a fonte de verdade. Na prática há duas escolas: code-first, em que o Spring gera o spec e o frontend gera tipos a partir dele (openapi-typescript para tipos puros, orval ou ng-openapi-gen para clientes com TanStack Query ou HttpClient já integrados); e spec-first, em que o spec é escrito à mão, versionado, e ambos os lados geram a partir dele. A primeira é a mais comum e funciona desde que a geração corra no CI do frontend contra o spec da versão do backend com que vai para produção — porque nessa altura uma quebra de contrato é um erro de compilação e não um undefined no ecrã.

A regra de evolução é a mesma do capítulo de APIs, com uma razão a mais: o browser do utilizador pode ter o bundle antigo durante horas (cache, aba aberta desde ontem). Portanto, só alterações aditivas — campos novos opcionais, endpoints novos —, nunca remover nem mudar o significado, e os campos removidos passam primeiro por deprecated no spec com uma data. Nos erros, o Spring devolve application/problem+json (o ProblemDetail do Spring 6) e o frontend tem um único tradutor: title e detail para a mensagem, status para a decisão (sessão expirada, sem permissão, conflito), e os campos de validação para os pôr ao lado dos inputs — o que exige que o backend devolva todos os erros de validação de uma vez, com o nome do campo tal como está no DTO.

Frontend e integração
SéniorMuito frequente
Como mantém o frontend e a API Spring de acordo? O que acontece quando o backend muda um campo?

Resposta-modelo

Com um contrato executável, não com uma página de documentação. O Spring expõe o OpenAPI através do springdoc; o CI do frontend descarrega o spec da versão do backend que vai para o mesmo ambiente e gera tipos — openapi-typescript para tipos, ou orval para clientes já ligados ao TanStack Query. A partir daí, cada resposta e cada corpo de pedido são tipados, e uma mudança incompatível no backend torna-se um erro de compilação no frontend antes de chegar a produção. Os tipos gerados são artefactos de build, não código que se edita.

Quando o backend «muda um campo», a pergunta é qual mudança. Acrescentar um campo opcional ou um endpoint é compatível e não exige coordenação. Renomear, remover ou mudar o tipo é uma quebra, e a regra é que não acontece num só passo: acrescenta-se o novo, marca-se o antigo como deprecated no spec com data, o frontend migra ao seu ritmo, e só depois se remove. A razão é que não controlo quando o browser do utilizador recarrega — um bundle de ontem pode estar a chamar a API de hoje —, portanto a API tem de servir as duas versões do frontend durante a janela.

Além dos tipos, protejo a fronteira em execução: o que vem da rede é validado contra um esquema (zod, gerado do mesmo spec) nos pontos onde uma forma errada seria catastrófica, porque os tipos são apagados e o servidor pode ter sido publicado com um bug. E os erros seguem um único formato — problem+json — com um tradutor no cliente que decide pelo status e mostra detail e os campos de validação, para que o frontend não tenha lógica de erros espalhada por cada chamada.

A camada que fecha o ciclo são testes de contrato: MSW nos testes de frontend com respostas geradas do spec (não escritas à mão), e do lado do Spring, testes que validam que as respostas reais cumprem o spec publicado. Se a organização for grande, contratos dirigidos pelo consumidor com Pact; se não, o CI com tipos gerados e um teste de smoke contra o backend real em staging chega.

43.2 Autenticação no browser: cookies HttpOnly, tokens, BFF e PKCE#

O capítulo 40 fixou onde o token pode viver; aqui está o desenho completo, do login ao logout, para os dois cenários que aparecem. Cenário A, aplicação própria com Spring Security: a forma mais simples e mais segura é sessão por cookie — login por POST, cookie HttpOnly; Secure; SameSite=Lax, CSRF pelo CookieCsrfTokenRepository com o token ecoado num cabeçalho, e o frontend não gere credenciais nenhumas. Funciona porque frontend e API estão na mesma origem (ver 43.3). Cenário B, identidade externa (Keycloak, Entra, Auth0): OAuth2/OIDC com Authorization Code e PKCE — o implicit flow está morto — e a decisão é quem faz a troca do código pelos tokens. Se for o browser (SPA pública), os tokens ficam em memória com refresh por rotação, e aceita-se a exposição a XSS durante a sessão. Se for um BFF — um serviço Spring na mesma origem, cliente OAuth2 confidencial —, o browser recebe apenas um cookie de sessão, os tokens nunca saem do servidor, e o BFF anexa-os às chamadas para a API. O BFF é a recomendação actual do grupo de trabalho OAuth para browsers, e o Spring Cloud Gateway com TokenRelay ou um OAuth2AuthorizedClientManager implementa-o em pouco código.

Frontend e integração
StaffMuito frequente
Desenhe a autenticação de uma SPA com Keycloak e uma API Spring. Onde ficam os tokens, como se renovam e como se faz logout?

Resposta-modelo

Proponho o padrão BFF, e explico porquê antes de desenhar. Uma SPA é um cliente público: qualquer coisa que guarde é lida por um XSS, e o refresh token — que vale por dias — é o que mais me preocupa. Com um BFF, o browser nunca vê tokens: tem um cookie de sessão HttpOnly; Secure; SameSite=Lax para um serviço na mesma origem, e é esse serviço, cliente confidencial do Keycloak, que guarda access e refresh token e os usa em nome do utilizador.

O fluxo: o utilizador clica em entrar; o BFF redirecciona para o Keycloak com Authorization Code e PKCE (mesmo sendo confidencial, PKCE protege contra injecção de código); o Keycloak autentica e volta ao BFF com o código; o BFF troca o código por tokens, guarda-os na sessão (Redis, ou cookie cifrado se quiser stateless), e responde ao browser com o cookie de sessão e um redireccionamento para a aplicação. A partir daí, a SPA chama /api/… na mesma origem; o BFF valida a sessão, anexa o access token como Bearer, e encaminha para a API Spring, que é um resource server puro — valida a assinatura do JWT com a chave pública do Keycloak e autoriza por claims, sem saber que existe um BFF.

Renovação: quando o access token está a expirar, o BFF usa o refresh token sozinho, de forma transparente para o browser, com um bloqueio por sessão para que dez pedidos concorrentes não façam dez renovações. A SPA só vê um 401 quando a sessão do BFF morre de vez, e aí redirecciona para o login. Logout: a SPA chama POST /logout no BFF, que invalida a sessão local, revoga os tokens no Keycloak e redirecciona para o end session endpoint do OIDC para fechar a sessão do fornecedor — senão o utilizador «sai» e o próximo clique em entrar volta a autenticar sem pedir a senha. Para as outras abas, um BroadcastChannel avisa-as.

O que se paga: mais um serviço a operar, estado de sessão a escalar, e a equipa de frontend a depender de um componente de backend para desenvolver — mitigado com um BFF de desenvolvimento em contentor. E quando não o faria: aplicações puramente estáticas sem backend próprio, onde a alternativa é a SPA pública com PKCE, tokens em memória, refresh com rotação e CSP estrita, aceitando explicitamente a exposição a XSS durante a sessão.

Modelação20 min

Desenhe, em texto, a sequência completa de pedidos entre browser, BFF, Keycloak e API para: (a) primeiro acesso não autenticado, (b) chamada à API com sessão válida, (c) renovação do token, (d) logout. A sua solução

Solução de referência

Os pontos que o avaliador procura no desenho: a troca do código acontece servidor a servidor com o client secret — o browser nunca vê tokens; a API é stateless e valida JWT por JWKS, sem conhecer o BFF, o que a torna reutilizável pela app móvel; a renovação tem bloqueio por sessão; o logout tem três passos (sessão local, revogação, sessão do fornecedor) e sem o terceiro o utilizador não saiu de verdade; e o CSRF está activo no BFF porque há cookies, e desactivado na API porque não há.

43.3 CORS, proxies e a mesma origem como decisão de arquitectura#

Com o mecanismo explicado no capítulo 40, a decisão aqui é simples de enunciar: evitar CORS é quase sempre melhor do que configurá-lo. Em desenvolvimento, o servidor do Vite ou do Angular CLI tem um proxy (server.proxy, proxy.conf.json) que encaminha /api para o Spring em localhost:8080 — o browser só vê uma origem. Em produção, o reverse proxy (nginx, o ingress do Kubernetes, o CDN) faz o mesmo: / serve os ficheiros estáticos, /api/ encaminha para o backend. Sem origens diferentes não há preflight, cookies SameSite funcionam por omissão, e o CSP fica mais simples. CORS configura-se apenas quando a API é genuinamente pública para outras origens — e aí com lista explícita de origens, maxAge no preflight, e nunca * com credenciais.

Exercício 43.2 — Quais destes pedidos fazem preflight?
Prever a saída6 min

A SPA em https://app.exemplo.pt chama https://api.exemplo.pt. Para cada pedido, diga se o browser envia um OPTIONS antes, e que cabeçalhos a resposta tem de trazer para o JavaScript poder ler o resultado.

A sua solução

Solução de referência

Um pedido é «simples» — sem preflight — quando o método é GET, HEAD ou POST, os cabeçalhos são só os safelisted (Accept, Accept-Language, Content-Language, Content-Type) e o Content-Type é um de application/x-www-form-urlencoded, multipart/form-data ou text/plain. É uma lista histórica: corresponde ao que um formulário HTML sempre pôde enviar sem JavaScript, e por isso não precisava de autorização prévia. Tudo o resto — JSON, Authorization, qualquer cabeçalho personalizado como X-Request-Id, qualquer outro método — dispara o OPTIONS.

Repare que mesmo os pedidos simples chegam ao servidor: o (4) cria a encomenda, e só a leitura da resposta pelo script é bloqueada se faltar o Allow-Origin. É por isso que CORS não é protecção contra CSRF — o formulário de um site terceiro faz o (4) na mesma — e é para isso que existem SameSite e o token anti-CSRF.

O (6) é o caso completo: com credentials: 'include', a resposta ao preflight e ao pedido real têm de trazer a origem explícita (o * é recusado pelo browser) e Access-Control-Allow-Credentials: true; e para o cookie ser sequer enviado entre origens diferentes, tem de ter SameSite=None; Secure, o que reabre a porta ao CSRF e obriga ao token. Este é o momento de dizer a frase de arquitectura: com um proxy na mesma origem, nenhum destes seis pedidos faz preflight, o cookie fica SameSite=Lax, e a configuração de CORS no Spring desaparece. O (3) e o (5) são também um argumento de latência — em APIs com muitas chamadas pequenas, o OPTIONS duplica as idas à rede, mitigado apenas pelo maxAge.

Frontend e integração
SéniorFrequente
O utilizador quer ver o estado da encomenda actualizar-se sem recarregar. Polling, SSE ou WebSocket — e como fica no Spring?

Resposta-modelo

SSE, e explico o critério: a comunicação é do servidor para o cliente, os eventos são pouco frequentes, e quero a solução com menos infraestrutura nova. SSE é HTTP normal com uma ligação que fica aberta e recebe eventos de texto; o EventSource do browser reconecta sozinho e envia o Last-Event-ID, portanto se a ligação cair durante uma mudança de rede o cliente recupera os eventos perdidos sem código meu. Passa em qualquer proxy que não faça buffering da resposta, e com HTTP/2 o limite antigo de seis ligações por origem deixa de ser problema.

No Spring, um SseEmitter por subscrição num controlador MVC, ou um Flux<ServerSentEvent> em WebFlux — mais natural para ligações longas, porque não prende uma thread por cliente. Os eventos vêm de onde as mudanças acontecem: o serviço que muda o estado publica num tópico (Kafka, ou um Sinks.many() em memória se houver uma instância), e o emissor filtra por utilizador. Com várias instâncias, é preciso um pub/sub partilhado — Redis ou o próprio Kafka — porque o cliente está ligado a uma instância e a mudança pode acontecer noutra. E identifico cada evento (id:) para o Last-Event-ID ter significado, o que obriga a conseguir reenviar eventos desde um identificador: uma tabela ou o offset do tópico.

Polling seria a resposta se a frequência fosse muito baixa e a infraestrutura não aguentasse milhares de ligações abertas — um GET a cada trinta segundos com ETag e 304 custa quase nada, e é honesto dizer que para «o estado da encomenda» pode chegar. WebSocket só se o cliente também enviasse muitas mensagens, ou se a latência de milissegundos importasse; traz um protocolo próprio, reconexão manual, e um balanceador que precisa de sticky sessions ou de um broker partilhado — para notificações de estado, é complexidade sem retorno.

No frontend, a subscrição vive no ciclo de vida do componente ou da rota — fechar o EventSource ao desmontar — e o evento não substitui o estado: invalida a query da encomenda (TanStack Query, ou o store) para que a UI vá buscar o estado completo. Assim o SSE é um sinal, não uma segunda fonte de verdade.

Uma lista de dezenas de milhares de encomendas. Como desenha a paginação entre a API e a UI?

Resposta-modelo

Por cursor, não por offset, e a razão vem dos dois lados. Do lado da base de dados, OFFSET 50000 obriga a ler e descartar cinquenta mil linhas — o custo cresce com a página. Do lado do utilizador, se entre duas páginas alguém inserir ou apagar uma encomenda, o offset muda de significado e a lista salta ou repete itens. Um cursor opaco — codificação da chave de ordenação do último item, tipicamente (criada_em, id) — dá WHERE (criada_em, id) < (?, ?) ORDER BY criada_em DESC, id DESC LIMIT 51: custo constante com um índice, páginas estáveis, e o 51 serve para saber se há mais sem contar. A API devolve { itens, proximoCursor } e o cliente não interpreta o cursor.

Na UI, a experiência decide o resto. Uma lista infinita usa useInfiniteQuery (ou o equivalente Angular) que guarda as páginas e pede a seguinte quando o último item entra no ecrã; uma tabela com «página 3 de 200» precisa de contagem total, que com cursor não existe — e aí a resposta honesta é uma contagem aproximada calculada à parte (uma vez, em cache), ou aceitar «seguinte/anterior» sem número de página, que é o que a maioria dos utilizadores usa de facto. Os filtros e a ordenação vão para o URL, para que a lista seja partilhável e sobreviva a recarregar; o cursor não vai, porque é uma posição efémera.

Independentemente da paginação, a UI só renderiza o que está visível — virtualização —, e o servidor impõe um limit máximo mesmo que o cliente peça mais. E se o utilizador precisa de «exportar tudo», isso não é paginação, é um trabalho assíncrono com um ficheiro no fim.

43.5 Monorepo, build e entrega: quem serve o frontend#

Há duas perguntas operacionais que aparecem sempre. Onde vive o código: um monorepo com Nx ou Turborepo dá pacotes partilhados (tipos gerados do contrato, o sistema de design, utilitários) com builds incrementais e cache remota, e é a escolha quando frontend e backend são a mesma equipa e saem juntos; repositórios separados são a escolha quando as equipas e as cadências são diferentes, e o contrato passa a ser o único ponto de contacto — versionado e publicado. Quem serve o frontend: dentro do JAR do Spring (em static/, com um forward das rotas da SPA para index.html) é a opção de menor infraestrutura, um único artefacto e a mesma origem por construção; separado, num CDN ou num contentor nginx, dá cache de borda, deploys independentes e um backend que não sabe que existe um frontend — ao custo de configurar o routing de origem única no proxy. Frontend e integração
SéniorFrequente
Como está organizado o build e o deploy de uma aplicação com frontend React e backend Spring? O que faria diferente em produto público contra ferramenta interna?

Resposta-modelo

Para uma ferramenta interna com uma equipa, a resposta preguiçosa e certa é um único artefacto: o build do frontend (Vite) corre no pipeline antes do Gradle ou Maven, os ficheiros vão para static/ no JAR, e o Spring serve a SPA com um controlador que encaminha rotas desconhecidas para index.html. Mesma origem por construção — sem CORS, cookies simples —, um deploy, uma versão, e nada de infraestrutura nova. Os cabeçalhos de cache configuram-se no Spring: imutável para os ficheiros com hash, no-cache para o index.html. O custo é o acoplamento: qualquer mudança no frontend é um deploy do backend, e vice-versa.

Para um produto público, separo: o frontend é um artefacto estático publicado num CDN (ou num contentor nginx atrás do ingress), com deploys independentes e cache de borda para o LCP em todas as geografias; o backend é uma API que não sabe que existe um frontend. A mesma origem mantém-se pelo routing — o CDN ou o ingress encaminha /api para o backend — ou, se as origens forem mesmo diferentes, entra um BFF. O pipeline tem duas cadências, e o contrato OpenAPI é o que as liga: o CI do frontend gera tipos contra a versão do backend em staging, e falha se houver quebra.

Em ambos os casos, três coisas não mudam. O index.html nunca é cacheado (senão os utilizadores ficam com bundles antigos para sempre) e os chunks têm hash no nome e cache de um ano. O deploy do frontend mantém os chunks da versão anterior no servidor durante algum tempo, porque uma aba aberta com a versão antiga vai pedir chunks antigos por lazy loading — e um 404 aí é uma página partida; a alternativa é o frontend detectar uma versão nova e sugerir recarregar. E o pipeline tem orçamentos: tamanho do bundle inicial e tempo de testes, ambos a falhar o build quando ultrapassados.

Monorepo com Nx ou Turborepo se a equipa é uma e há código partilhado — o pacote de tipos gerados, o sistema de design; repositórios separados se as equipas e cadências são diferentes, e aí o contrato é publicado como pacote versionado. Não sou religioso sobre isto; sou sobre o index.html sem cache e os chunks antigos disponíveis.

43.6 Erros, observabilidade e feature flags do lado do cliente#

A observabilidade do backend termina no load balancer; a do produto começa no browser. Três peças ligam os dois mundos. Um identificador de correlação gerado no cliente (ou pelo gateway, propagado como traceparent do W3C ou X-Request-Id), enviado em cada pedido, posto no MDC dos logs do Spring por um filtro, incluído nos traces, e devolvido no problem+json para o utilizador o poder citar — «deu-me erro» transforma-se num identificador para pesquisar. Captura de erros no cliente (Sentry ou equivalente): excepções não tratadas, rejeições de promessas, erros de boundaries, com contexto (versão do bundle, rota, utilizador anonimizado, últimas acções) e source maps carregados no CI para que o stack trace minificado seja legível — mais os Core Web Vitals reais (RUM), que são a única medição de performance que conta. Feature flags avaliadas no servidor e entregues ao cliente como um conjunto de booleanos por utilizador: o cliente decide o que mostrar, o servidor decide o que autorizar — uma flag que só existe no frontend não é uma flag de segurança, é uma sugestão.

Frontend e integração
SéniorFrequente
Um utilizador diz que «deu erro ao pagar». Como chega do relato ao registo do servidor, e o que já devia estar montado para isso demorar dois minutos?

Resposta-modelo

O que devia estar montado: um identificador de correlação que atravessa tudo. O frontend gera um X-Request-Id por pedido (ou propaga o traceparent que o gateway inicia), o Spring apanha-o num filtro e põe-no no MDC para que todas as linhas de log daquele pedido o tenham, o tracing distribuído usa-o como identificador de trace, e o problem+json devolve-o no corpo — e a UI mostra-o na mensagem de erro: «Não foi possível concluir o pagamento. Código de apoio: 7f3a…». O utilizador cita o código; eu procuro-o nos logs e no tracing e tenho o pedido completo, com as chamadas ao gateway de pagamento e os tempos de cada uma.

Do lado do cliente, o Sentry (ou equivalente) captura o erro com contexto: versão do bundle, rota, o breadcrumb das últimas acções e pedidos, o browser e o dispositivo, e o mesmo identificador de correlação como tag — o que permite ir do evento no Sentry ao trace no backend com um clique. Isto exige source maps carregados no CI a cada deploy, senão o stack trace é minificado e inútil, e uma release identificada para saber que versão o utilizador tinha.

Sem o código de apoio, o caminho é mais longo mas ainda possível: o utilizador identificado (ou a sessão), a janela temporal, e o filtro por rota de pagamento no Sentry e por endpoint nos logs. É aqui que se vê se a observabilidade foi desenhada ou improvisada.

Duas notas de senioridade. A mensagem para o utilizador nunca inclui o detail técnico do servidor — inclui o que ele pode fazer e o código; o detalhe fica no log. E os erros que o utilizador vê são uma métrica de produto: uma taxa de erro na página de pagamento acima de um limiar dispara um alerta, porque «deu erro ao pagar» não devia chegar por relato — devia chegar por alarme antes do relato.

Frontend e integração
MidOcasional
Como faz feature flags numa aplicação com frontend e backend? Onde se avaliam?

Resposta-modelo

Avaliam-se no servidor e entregam-se ao cliente já decididas. O backend (ou o serviço de flags — Unleash, LaunchDarkly, ou uma tabela própria) avalia as regras para o utilizador autenticado — percentagem, segmento, lista de beta — e a API expõe um endpoint que devolve o conjunto de booleanos; o frontend carrega-o no arranque, guarda-o em memória, e usa-o para mostrar ou esconder. A razão de avaliar no servidor é dupla: as regras não vão para o bundle (não expõem a estratégia de lançamento nem são manipuláveis), e a mesma avaliação serve o backend, que é onde a flag tem de ser verdadeiramente imposta.

Esse é o ponto que separa: uma flag só no frontend esconde um botão, mas o endpoint continua a aceitar o pedido de quem o descobrir. Se a funcionalidade tem consequências — um novo tipo de pagamento —, a flag é verificada também no serviço, e a do frontend é só experiência. Para a decisão ser consistente nos dois lados, ambos avaliam com o mesmo identificador de utilizador e a mesma semente, ou o frontend recebe a decisão do backend em vez de a calcular.

Operacionalmente: flags têm dono e data de remoção, porque uma flag permanente é um if permanente com dois caminhos por testar; o kill switch de uma funcionalidade nova é a flag mais valiosa; e as flags entram nos eventos de analytics e nos erros do Sentry como tags, para se saber que variante o utilizador tinha quando algo correu mal.

SéniorAvaliação no servidor, imposição no backend, experiência no frontend, consistência entre os dois, e higiene de remoção.
StaffLiga a analytics e erros, discute flags em SSR e cache, e o processo de lançamento progressivo com kill switch.

  • Flags sem dono nem data de remoção.
  • Regras de lançamento no bundle.
Frontend e integração
SéniorMuito frequente
React ou Angular para o próximo produto, com uma equipa de backend Java que vai fazer full-stack?

Resposta-modelo

Respondo com critérios antes de responder com um nome, porque a pergunta está a testar se tenho uma opinião fundamentada ou uma preferência. Os dois são maduros, os dois fazem tudo o que um produto precisa, e a diferença está em três eixos: quanta estrutura vem de fábrica, como é o ecossistema, e o que a equipa já sabe.

Angular vem com tudo decidido — router, formulários, HTTP, injecção de dependências, testes, CLI — e o resultado é que dois projectos Angular se parecem um com o outro e um programador de Java reconhece a arquitectura em cinco minutos. Para uma equipa de backend que vai fazer full-stack, isso é uma vantagem real: menos decisões, menos bikeshedding, TypeScript estrito por omissão, e uma migração de versão gerida pelo CLI. O custo é a curva de aprendizagem de RxJS e da change detection, e um ecossistema mais pequeno.

React é uma biblioteca com um ecossistema: cada projecto escolhe router, dados, formulários, estilo, e o resultado depende de quem escolhe. A vantagem é a flexibilidade e a dimensão do ecossistema — qualquer componente, qualquer integração, existe primeiro para React —, e com Next.js e Server Components há um caminho para páginas de conteúdo rápidas que Angular só começa a ter. O custo é exactamente a flexibilidade: uma equipa sem experiência de frontend faz escolhas más nas primeiras semanas e vive com elas dois anos, e a disciplina dos hooks é menos intuitiva do que parece — os exercícios do capítulo 41 são a prova.

Para a equipa descrita — backend Java, a começar — recomendaria Angular, com signals, standalone e OnPush desde o primeiro dia, porque a estrutura imposta é o que uma equipa sem experiência de frontend mais precisa e o modelo de injecção é o que já conhecem. Mudaria para React se o produto fosse público com conteúdo indexável (Next.js), se houvesse gente de frontend com experiência de React para fixar as convenções, ou se dependesse de um ecossistema específico — visualização de dados, editores ricos. E o que não faria em nenhum dos casos é decidir sem um spike de duas semanas com a equipa real a fazer uma funcionalidade real nos dois.

43.7 Resumo e checklist#

A integração é onde o full-stack se distingue: as decisões certas são quase todas de fronteira — contrato, origem, sessão, entrega — e são as que um programador só de frontend ou só de backend deixa para «o outro lado».

  • Contrato executável: OpenAPI do Spring, tipos gerados no CI contra a versão a publicar, evolução aditiva com deprecated, validação de esquema na fronteira onde importa.
  • O browser pode ter o bundle de ontem: a API serve as duas versões durante a janela; os chunks antigos ficam no servidor; o index.html nunca é cacheado.
  • problem+json com um único tradutor no cliente; todos os erros de validação de uma vez, com o nome do campo do DTO.
  • Autenticação: sessão por cookie com Spring Security quando a identidade é própria; BFF com Authorization Code + PKCE quando é externa; tokens nunca no storage; logout em três passos.
  • Mesma origem por proxy (Vite em dev, nginx/ingress em prod) elimina CORS, preflight e SameSite=None. CORS só para APIs genuinamente públicas, com origens explícitas e maxAge.
  • Pedido simples: GET/HEAD/POST, cabeçalhos safelisted, Content-Type de formulário. JSON, Authorization e qualquer outro método fazem preflight.
  • SSE para servidor → cliente; WebSocket só se for bidireccional; polling com ETag quando a frequência é baixa. O evento invalida, não substitui.
  • Paginação por cursor com chave composta e limit + 1; filtros no URL; virtualização; limite no servidor.
  • Entrega: dentro do JAR para ferramenta interna; CDN ou nginx para produto público; orçamentos de bundle no CI.
  • Correlação de ponta a ponta mostrada ao utilizador, Sentry com source maps, RUM para performance, flags avaliadas no servidor e impostas no backend.

Checklist de preparação para as 48 horas antes da entrevista:

  • Resolver o Exercício 43.2 e saber a definição de «pedido simples» de cor.
  • Desenhar o fluxo BFF do Exercício 43.1 no papel em cinco minutos, com os quatro cenários.
  • Ter a Tabela 43.1 na cabeça e um exemplo real de cada coluna.
  • Explicar a paginação por cursor com a consulta SQL e o contrato da API.
  • Saber o que acontece a uma aba aberta há dois dias depois de um deploy, e o que já está montado para isso.
  • Ter a resposta «React ou Angular» pronta com três critérios e uma recomendação condicionada.

Um Java sénior que «também faz frontend» é avaliado nesta parte de uma forma particular: ninguém espera que saiba de cor a API de um framework, mas toda a gente espera que perceba o que muda quando o programa corre numa máquina que não controla, sobre uma rede que não confia, numa única thread que também tem de pintar o ecrã. Este capítulo é o transversal — o que se pergunta antes de chegar ao React ou ao Angular e o que os dois capítulos seguintes assumem como sabido: TypeScript como sistema de tipos estrutural, o event loop com a ordem exacta de microtasks e macrotasks, CORS e cookies, os números de performance que o browser mede, e uma pirâmide de testes que está ao contrário da do backend.

40.1 O que muda quando o cliente é um browser#

Cinco coisas mudam, e a resposta forte a «que diferenças vê entre programar backend e frontend» enumera-as com a consequência de cada uma. A máquina não é sua: o código corre num dispositivo com CPU e memória desconhecidas, numa versão de browser que não escolheu, com extensões a mexer no DOM — o que obriga a medir no percentil, não na sua máquina. A rede está no caminho crítico: cada byte de JavaScript é descarregado, analisado e compilado antes de o utilizador ver alguma coisa, e uma dependência de 200 KB custa mais do que a funcionalidade que trouxe. Há uma thread só: o mesmo fio executa o seu código e pinta o ecrã; um cálculo de 200 ms é 200 ms de interface congelada, e é por isso que tudo o que é I/O é assíncrono por desenho. O cliente é hostil: qualquer validação no browser é uma conveniência de UX, não uma regra de negócio, e qualquer segredo que chegue ao browser é público. O estado é efémero e duplicado: o que está na memória da página desaparece numa recarga, e o que está em cache pode estar desactualizado em relação ao servidor — gerir essa duplicação é metade do trabalho de um frontend.

Em entrevista, o sinal de senioridade é ligar cada uma destas a uma decisão: «como o cliente é hostil, a autorização é no servidor e a UI só esconde botões»; «como há uma thread, o parsing de um CSV grande vai para um Web Worker»; «como o estado é duplicado, uso uma biblioteca de estado de servidor com invalidação em vez de copiar respostas para um store».

Frontend e integração
MidMuito frequente
Vem do backend. O que é que muda, na sua cabeça, quando o código passa a correr no browser?

Resposta-modelo

Mudam as garantias. No backend controlo a máquina, a versão do runtime, a rede interna e a confiança nos chamadores; no browser perco as quatro. A consequência prática mais importante é a confiança: nenhuma validação no cliente substitui a do servidor, nenhum segredo pode estar no bundle, e a autorização decide-se na API — a UI limita-se a não mostrar o que o utilizador não pode fazer, para não o frustrar, não para o impedir.

A segunda mudança é o modelo de execução. Há uma única thread que corre o meu código e pinta o ecrã, por isso qualquer trabalho síncrono longo congela a interface — e por isso todo o I/O é assíncrono e o event loop passa a fazer parte do raciocínio diário. Um for sobre cem mil elementos que no servidor é ruído, no browser é um frame drop visível; a resposta é dividir o trabalho, ou mandá-lo para um Web Worker.

A terceira é a rede no caminho crítico: cada dependência é código que o utilizador descarrega e compila antes de interagir. Passo a olhar para o tamanho do bundle como olho para uma consulta N+1 — é o custo escondido que se acumula sem ninguém reparar — e a dividir o código por rota para que a primeira página não pague pelas outras.

A quarta é o estado: a página tem uma cópia dos dados que pode estar velha, e desaparece na recarga. Gerir isso bem significa distinguir estado de interface (que aba está aberta, um formulário a meio) de estado de servidor (a lista de encomendas), e tratar o segundo como cache com invalidação, não como fonte de verdade. E, ligado a tudo isto, a medição: o que interessa não é o meu portátil, é o p75 de um telemóvel médio em 4G — os Core Web Vitals existem para isso.

40.2 TypeScript a sério: tipos estruturais, narrowing e unions discriminadas#

A diferença que um Java sénior tem de interiorizar antes de escrever TypeScript é que os tipos são formas, não nomes. Duas interfaces com os mesmos campos são o mesmo tipo; um objecto com campos a mais é atribuível a um tipo com menos; e uma classe é um tipo pela forma das suas instâncias, não pela sua identidade — instanceof continua a existir, mas o compilador não o usa para decidir atribuições. A única excepção, e é a pergunta clássica, é o excess property check: quando se atribui um literal de objecto directamente a um tipo, propriedades a mais são erro, porque quase sempre são um engano de escrita. Através de uma variável intermédia, a tipagem estrutural volta a valer.

A segunda ideia é o narrowing: o tipo de uma variável muda ao longo do fluxo conforme o que o compilador consegue provar. typeof, instanceof, in, comparações de igualdade e type predicates (x is Foo) estreitam uma união até um membro; e o padrão que substitui a hierarquia de classes do Java é a union discriminada — vários tipos de objecto com um campo literal comum (tipo: 'circulo' | 'quadrado') que o switch usa para estreitar, com exaustividade verificada quando o default atribui a never. É o equivalente exacto de sealed mais pattern matching em Java 21, e dizê-lo em voz alta é uma ponte que o entrevistador aprecia.

Os tipos não existem em execução. Um as Utilizador sobre a resposta de fetch não verifica nada — é uma promessa ao compilador que o servidor pode quebrar. Na fronteira com o exterior valida-se com um esquema (zod, valibot) ou com tipos gerados do OpenAPI, e só depois se confia no tipo. É a mesma disciplina que o @Valid no controlador Spring.

Frontend e integração
MidMuito frequente
Qual é a diferença entre any e unknown? E entre uma interface em TypeScript e uma em Java?

Resposta-modelo

any e unknown aceitam ambos qualquer valor; a diferença é o que deixam fazer a seguir. Com any pode-se chamar qualquer método e atribuir a qualquer tipo — é desligar o compilador naquela variável, e o erro aparece em execução, longe da origem. Com unknown não se pode fazer nada até estreitar o tipo: typeof x === 'string', instanceof, ou uma validação com esquema. É a escolha certa para tudo o que vem de fora — JSON.parse, respostas HTTP, o e de um catch — porque obriga a tratar a fronteira. Na prática, any só aparece em migrações e com noImplicitAny ligado para não entrar por acidente.

Sobre interfaces, a diferença é estrutural contra nominal. Em Java, uma classe só é um Pagavel se declarar implements Pagavel; em TypeScript, qualquer objecto com a forma certa é um Pagavel, declare-o ou não. Isso tem duas consequências: implements em TypeScript é apenas uma verificação de que a classe cumpre a forma, não uma marca de identidade; e dois tipos com a mesma estrutura são intercambiáveis mesmo que representem conceitos diferentes — UserId e OrderId ambos string misturam-se sem erro, e é para isso que existem branded types.

A interface de TypeScript também não existe em execução — é apagada na compilação, como os genéricos em Java, mas mais radicalmente: não há instanceof para interfaces, e um objecto que chegue da rede com a forma errada passa pelo compilador sem queixa se tiver sido anotado com as. Daí a regra: tipo estático dentro da aplicação, validação de esquema na fronteira.

A ponte que costumo fazer em entrevista é com sealed: o que em Java modelaria com uma hierarquia selada e switch com padrões, em TypeScript é uma union discriminada com um campo literal e never no default para a exaustividade. É o mesmo desenho, e o compilador dá o mesmo aviso quando se acrescenta um caso.

40.3 O event loop do browser: microtasks, macrotasks e o que bloqueia a UI#

O modelo é simples de enunciar e é onde a maioria dos exercícios de «o que imprime» do frontend são construídos. Há uma pilha de chamadas, uma fila de microtasks (continuações de promises, await, queueMicrotask, MutationObserver) e várias filas de macrotasks (timers, eventos de I/O e de utilizador, mensagens). O ciclo é: executar uma macrotask até a pilha esvaziar; esvaziar toda a fila de microtasks, incluindo as que forem acrescentadas entretanto; se for altura de pintar, correr os requestAnimationFrame e pintar; pegar na macrotask seguinte. Três consequências que valem perguntas: uma microtask corre sempre antes de qualquer timer, mesmo setTimeout(…, 0); um ciclo de microtasks que se realimenta nunca deixa o browser pintar; e await não «liberta» a thread para o timer — apenas para outras microtasks.

Para o entrevistador, isto liga-se ao que bloqueia a UI. Um cálculo síncrono de 300 ms trava a pintura e os eventos por 300 ms; dividi-lo em pedaços com setTimeout ou scheduler.yield() deixa o browser respirar entre pedaços; mandá-lo para um Web Worker tira-o da thread principal de todo. A métrica que mede isto é o INP (interação até à pintura seguinte) — e é por isso que «o que faz com um cálculo pesado» é uma pergunta de performance e de event loop ao mesmo tempo.

Frontend e integração
SéniorMuito frequente
Explique o event loop. Porque é que setTimeout(fn, 0) corre depois de um await que já resolveu?

Resposta-modelo

O JavaScript do browser corre numa única thread com uma pilha de chamadas e duas classes de filas. As macrotasks — timers, eventos de utilizador, respostas de rede, mensagens — são tarefas independentes que o event loop pega uma de cada vez. As microtasks — continuações de promises, o que vem depois de um await, queueMicrotask — são processadas todas, até a fila esvaziar, no fim de cada macrotask e antes de o browser ter oportunidade de pintar ou de pegar na macrotask seguinte.

Daí a resposta à pergunta: await numa promise já resolvida não continua imediatamente — agenda a continuação como microtask. E o setTimeout(fn, 0) agenda uma macrotask, que só é considerada depois de a fila de microtasks estar vazia. Portanto a continuação do await corre primeiro, sempre, independentemente da ordem em que foram escritos. Vale a pena dizer a regra completa: o código síncrono da tarefa actual corre até ao fim; depois todas as microtasks, incluindo as que essas microtasks criem; só depois um timer.

As consequências práticas são três, e são as que interessam a quem opera aplicações. Primeira, um ciclo de microtasks que se realimenta (uma promise que agenda outra, sem fim) nunca devolve o controlo ao browser — a página congela sem nenhum ciclo while à vista. Segunda, «ceder» ao browser entre pedaços de trabalho pesado exige uma macrotask (setTimeout, scheduler.yield(), MessageChannel), não um await Promise.resolve(), que é apenas uma microtask. Terceira, para trabalho de CPU a sério, o event loop não é a resposta — é um Web Worker, que tem a sua própria thread e comunica por mensagens.

A ligação a Java que costumo fazer: é o modelo de um único event loop do Netty ou do Vert.x — uma thread que nunca pode bloquear, com I/O assíncrono por baixo — só que aqui a thread também pinta o ecrã, e o preço de bloquear é visível ao utilizador em vez de ao load balancer.

Exercício 40.2 — Prever a saída: microtasks, macrotasks e async
Prever a saída6 min

Escreva a ordem exacta em que as letras e números aparecem na consola. Os dois blocos correm um a seguir ao outro no mesmo script.

A sua solução

Solução de referência

Primeiro corre tudo o que é síncrono no script: 1; o timer de 2 é posto na fila de macrotasks; 3 e 4 entram na fila de microtasks; a função async executa sincronamente até ao primeiro await — por isso 5 aparece já — e o await null agenda a continuação (6) como microtask, atrás de 3 e 4; 7 fecha o código síncrono. Os dois timers do segundo bloco entram na fila de macrotasks atrás de 2.

Esvazia-se então a fila de microtasks pela ordem de chegada: 3, 4, 6. Só depois o event loop pega na primeira macrotask, 2. A seguir, a macrotask de A: imprime A e agenda B como microtask — e como as microtasks se esvaziam entre macrotasks, B corre antes de C, apesar de o timer de C já estar na fila há muito.

As duas armadilhas que este exercício apanha: pensar que uma função async «arranca mais tarde» (arranca já; só a parte depois do await é adiada) e pensar que timers com o mesmo atraso correm seguidos sem interrupção (qualquer microtask criada no primeiro corre antes do segundo). É este segundo ponto que faz com que um ciclo de promises que se realimentam bloqueie todos os timers e a pintura.

40.4 HTTP do lado do cliente: CORS, cookies, cache e onde guardar o token#

CORS é a pergunta em que mais candidatos full-stack se atrapalham, porque a percebem como um mecanismo do servidor quando é uma política do browser. A regra base é a same-origin policy: um script carregado de app.exemplo.pt pode enviar pedidos a api.exemplo.pt, mas o browser não deixa o script ler a resposta a menos que o servidor a autorize com Access-Control-Allow-Origin. Para pedidos que não são «simples» — método fora de GET/HEAD/POST, cabeçalhos além dos permitidos, Content-Type: application/json — o browser envia antes um OPTIONS de preflight e só faz o pedido real se a resposta o autorizar. Três consequências práticas: CORS não protege o servidor (o curl não o respeita — é protecção do utilizador contra sites terceiros); Allow-Origin: * não se combina com credenciais; e cada preflight é uma ida à rede a mais, que se elimina pondo frontend e API na mesma origem através de um proxy ou de um BFF.

Frontend e integração
SéniorMuito frequente
O frontend em app.exemplo.pt chama a API em api.exemplo.pt e o browser dá erro de CORS. O que está a acontecer e como resolve?

Resposta-modelo

Primeiro corrijo a percepção: o pedido provavelmente chegou ao servidor. CORS é uma política do browser — o script de uma origem só pode ler a resposta de outra origem se essa resposta trouxer Access-Control-Allow-Origin com a origem do chamador. Se o pedido não for «simples» (aqui será um POST com JSON ou um GET com Authorization), o browser envia antes um OPTIONS de preflight, e se esse falhar o pedido real nem sai. O erro na consola é o browser a recusar entregar a resposta ao JavaScript, não a API a recusar o pedido.

Diagnostico no separador de rede: vejo se há um OPTIONS e o que respondeu. Os erros típicos são o servidor não responder ao OPTIONS (um 401 do filtro de autenticação a apanhar o preflight, que não leva credenciais), o Allow-Origin não corresponder exactamente à origem (esquema e porta contam), faltar Allow-Headers para Authorization ou Content-Type, e o clássico: Allow-Origin: * com credentials: 'include', que o browser rejeita — com cookies a origem tem de ser explícita e tem de vir Allow-Credentials: true.

A correcção depende de a API ser minha ou não. Se for, em Spring configuro CorsConfigurationSource com a lista de origens permitidas, métodos, cabeçalhos e maxAge no preflight para não repetir o OPTIONS em cada chamada — e garanto que o filtro de segurança deixa passar o OPTIONS. Mas a resposta de arquitectura, que é a que ganha pontos, é evitar CORS de todo: servir frontend e API a partir da mesma origem, com um reverse proxy (nginx, o ingress) a encaminhar /api para o backend, ou com um BFF. Sem origens diferentes não há preflight, os cookies SameSite funcionam sem truques, e desaparece uma classe inteira de configuração.

Fecho com o que CORS não é: não é segurança do servidor. Um curl ou um serviço ignoram-no completamente. Protege o utilizador de um site terceiro usar o browser dele para ler dados da minha API com os cookies dele; a autorização da API continua a ter de ser feita pela API.

Frontend e integração
SéniorMuito frequente
Onde guarda o token de acesso numa SPA? Defenda a escolha contra XSS e CSRF.

Resposta-modelo

A regra que decide tudo: o que o JavaScript consegue ler, um XSS consegue roubar. Por isso localStorage e sessionStorage estão fora para credenciais — um único script de terceiros comprometido, uma dependência com um postinstall malicioso, e o token sai para um servidor alheio sem o utilizador notar. A escolha por omissão é um cookie HttpOnly, Secure e SameSite=Lax (ou Strict, se a aplicação não precisar de chegar por ligações externas): o script não lhe toca, viaja só por TLS, e não é enviado em pedidos iniciados por outros sites, o que fecha a maior parte do CSRF.

O cookie traz o seu próprio risco, CSRF, e a resposta tem de o cobrir: SameSite trata da maioria, e para o que resta (browsers antigos, SameSite=None por necessidade) uso um token anti-CSRF — o padrão double submit ou o CsrfTokenRepository do Spring Security com o token num cookie legível e ecoado num cabeçalho. Também garanto que operações com efeitos só respondem a POST/PUT/DELETE, nunca a GET.

A versão mais robusta é o BFF: o browser nunca vê um token OAuth2; tem apenas uma sessão opaca num cookie, e é o serviço BFF, na mesma origem, que guarda access e refresh tokens e os anexa às chamadas para a API. Isto remove o token do alcance do XSS, centraliza o refresh e a revogação, e de caminho elimina CORS. O custo é um serviço a mais e estado de sessão a escalar — cookies cifrados ou Redis.

Quando cookies não são opção — API de terceiros, aplicação móvel híbrida —, o compromisso é o token em memória (numa variável, nunca em storage) com um refresh token em cookie HttpOnly para sobreviver à recarga, e com PKCE no fluxo de autorização. Aceita-se que um XSS possa usar o token enquanto a página está aberta, mas não que o persista; e mitiga-se XSS na origem com Content-Security-Policy estrita e sem innerHTML com dados externos.

  • Não saber que o BFF existe.

40.5 Performance percebida: Core Web Vitals, bundles e o custo de cada dependência#

Performance no frontend mede-se pelo que o utilizador percebe, e o Google fixou o vocabulário: LCP (tempo até o maior elemento visível estar pintado; bom até 2,5 s), INP (latência entre uma interacção e a pintura seguinte, no pior caso da sessão; bom até 200 ms) e CLS (quanto o layout salta enquanto carrega; bom até 0,1). Medem-se no campo (RUM, web-vitals) no p75, não no laboratório, e cada uma tem causas típicas: LCP alto é JavaScript a mais antes do conteúdo, imagens sem dimensões ou sem prioridade, e servidor lento; INP alto é trabalho síncrono longo na thread principal — o event loop outra vez; CLS é imagens e anúncios sem espaço reservado e fontes que trocam tarde.

A alavanca maior é o bundle. Cada dependência é código que o utilizador descarrega, analisa e compila; uma biblioteca de datas «completa» são 70 KB para formatar uma data, e um gráfico bonito são 300 KB numa página que a maioria nunca abre. As respostas que se esperam: code splitting por rota e por componente pesado (import() dinâmico, React.lazy, loadComponent nas rotas Angular, @defer), tree shaking que só funciona com ESM e importações nomeadas, análise do bundle antes de aceitar uma dependência (bundlephobia, o analyzer do Vite/Angular), e imagens com formato moderno, dimensões explícitas e lazy loading fora do ecrã inicial.

Frontend e integração
SéniorFrequente
A página inicial demora quatro segundos a mostrar conteúdo em telemóvel. Por onde começa?

Resposta-modelo

Começo por confirmar a medição: dados de campo no p75 (Search Console, RUM, a biblioteca web-vitals) e não um Lighthouse no meu portátil, porque a distribuição de dispositivos é o problema. Depois decomponho o LCP em quatro fases, que o próprio browser expõe: tempo até ao primeiro byte, atraso até começar a carregar o recurso principal, carregamento desse recurso, e atraso de renderização. Cada fase aponta para um culpado diferente, e é raro a resposta ser «tudo».

Na experiência, a causa mais comum em SPAs é a fase de renderização: o conteúdo só aparece depois de descarregar, analisar e executar o bundle inteiro, e ainda esperar por uma chamada à API. As correcções por ordem de retorno: dividir o bundle por rota para que a primeira página não pague pelas outras; adiar tudo o que não é crítico (analytics, chat, gráficos) para depois da interacção; e, se a página inicial é conteúdo, renderizá-la no servidor — SSR com hidratação, ou Server Components — para que o HTML chegue pronto e o JavaScript só acrescente interactividade.

Se a fase lenta for o recurso, é quase sempre a imagem principal: sem fetchpriority="high", sem dimensões, em formato pesado, ou atrás de um lazy loading que não devia estar no ecrã inicial. Se for o primeiro byte, o problema é do servidor ou do CDN — e aí volto a ser backend: cache de borda para o HTML, compressão, ligação keep-alive.

O que não faço é optimizar às cegas. Uma dependência de 200 KB tira-se depois de o analyzer mostrar que está no bundle inicial; um React.memo põe-se depois de o profiler mostrar re-renders caros. E defino um orçamento — tamanho do bundle inicial e LCP no p75 — verificado no CI, porque performance que não é medida no pipeline regride na segunda semana.

MidFrequente
Um colega quer adicionar uma biblioteca de 300 KB para um componente de calendário. Como decide?

Resposta-modelo

A pergunta não é «é boa», é «quanto custa a quem» — e o custo no frontend paga-se em três moedas. Tamanho: 300 KB minificados são talvez 90 KB comprimidos, mas o browser tem de descomprimir, analisar e compilar os 300; num telemóvel médio isso são centenas de milissegundos de thread principal. Se entrar no bundle inicial, todos os utilizadores pagam, incluindo os que nunca abrem o calendário. Superfície: uma dependência é código que não revemos, com as suas próprias dependências e o seu próprio calendário de vulnerabilidades. Acoplamento: substituí-la daqui a dois anos custa o que custar reescrever todos os sítios que a usam.

O que faço antes de decidir: vejo o tamanho real com importações nomeadas e tree shaking (muitas bibliotecas «grandes» reduzem a 20 KB se só importarmos o que usamos; outras não, porque não são ESM); vejo se o browser já faz aquilo — <input type="date"> cobre o caso simples, Intl.DateTimeFormat trata da formatação — e vejo se uma alternativa mais pequena chega (existe quase sempre). Se ainda assim compensar, entra por import() dinâmico, só quando o componente aparece, e nunca no bundle inicial.

A conversa com o colega é sobre critérios, não sobre gosto: qual é o orçamento de bundle da rota, quanto é que esta biblioteca gasta dele, e o que ganhamos que não conseguimos em duzentas linhas nossas. Se a resposta for «acessibilidade de teclado e localização em quarenta idiomas», provavelmente compensa; se for «tem um picker bonito», provavelmente não. E registamos a decisão, porque é o tipo de coisa que se questiona seis meses depois.

40.6 Testes e qualidade no frontend: a pirâmide invertida#

A pirâmide de testes do backend — muitos unitários, alguns de integração, poucos de ponta a ponta — não se transpõe directamente. No frontend, a unidade que interessa é o componente com o utilizador à frente, e testes unitários de funções puras são poucos porque a lógica pura é pouca. A forma que funciona é um trapézio: uma base de testes de componente que renderizam e interagem como o utilizador (Testing Library, Vitest ou Jest, com o DOM simulado), com a rede substituída por MSW ao nível de HTTP para que o código de fetch real corra; uma camada de testes de ponta a ponta com Playwright para os fluxos críticos (login, checkout), poucos e estáveis; e, ao lado, testes visuais de regressão se o produto viver do aspecto.

A filosofia da Testing Library resume-se numa frase que os entrevistadores gostam de ouvir citada: quanto mais os testes se parecerem com a forma como o software é usado, mais confiança dão. Na prática: consultar por papel acessível e texto (getByRole('button', { name: 'Guardar' })) em vez de por classe ou test id, interagir com userEvent em vez de chamar métodos, e nunca afirmar sobre estado interno. Isto tem um efeito lateral valioso — obriga o componente a ser acessível, porque um botão sem nome acessível não é encontrável — e um custo que se assume: os testes ficam mais lentos que um teste unitário puro, o que é aceitável porque testam o que importa.

Frontend e integração
SéniorFrequente
Como testa um frontend? O que testa em cada camada, e o que deliberadamente não testa?

Resposta-modelo

A base são testes de componente que se comportam como um utilizador: renderizo o componente com as dependências reais possíveis, procuro elementos pelo papel e pelo texto acessível, interajo com userEvent e afirmo sobre o que o utilizador veria. A rede não se simula ao nível da função — uso MSW para interceptar HTTP, de forma a que o código de fetch, o tratamento de erros e a biblioteca de dados corram a sério contra respostas controladas. Um teste típico: «ao submeter o formulário com um e-mail inválido, aparece a mensagem de erro e o pedido não é feito».

Por cima, poucos testes de ponta a ponta com Playwright, contra a aplicação a correr com um backend real ou simulado ao nível da rede: os três a cinco fluxos que se falharem custam dinheiro. Poucos porque são lentos e frágeis por natureza; estáveis porque usam localizadores acessíveis e esperas explícitas, não sleeps. E ao lado, testes unitários clássicos para o pouco que é lógica pura — formatação, cálculos, redutores de estado — que são rápidos e baratos.

O que não testo, e digo-o porque é a parte que distingue: detalhes de implementação — se um hook foi chamado, o estado interno de um componente, classes CSS —, porque esses testes partem a cada refactor sem apanhar bugs. Não uso snapshots de árvores inteiras, que degeneram em «aprovar tudo»; uso-os, quando uso, em fragmentos pequenos e intencionais. E não testo o framework: que um useState actualiza, que o @Input chega — isso é confiança que já comprei ao escolher a ferramenta.

Duas coisas complementam a pirâmide sem ser testes: TypeScript estrito, que elimina uma classe inteira de testes de «e se passarem null», e verificação de acessibilidade automatizada (axe) nos testes de componente, que apanha o que ninguém testa à mão. E no CI, tudo corre em paralelo com um limite de tempo, porque uma suite de frontend de vinte minutos é uma suite que se começa a saltar.

Frontend e integração
MidFrequente
O que é acessibilidade na prática, e o que verifica antes de dar um componente por terminado?

Resposta-modelo

Acessibilidade é o componente funcionar para quem não usa rato nem vê o ecrã da mesma forma — e, na prática, é sobretudo usar HTML semântico em vez de div com handlers. Um <button> traz teclado, foco e papel sem código; uma div onClick não traz nada e obriga a reinventar tudo mal. A verificação que faço tem cinco pontos: navego o componente só com teclado (Tab chega a tudo, Enter e Espaço activam, Escape fecha, o foco é visível); cada controlo tem um nome acessível (rótulo associado, aria-label quando o texto não chega); imagens informativas têm alt e decorativas têm alt=""; o contraste cumpre 4,5:1; e mensagens dinâmicas — erros de validação, «guardado» — são anunciadas com aria-live ou por foco.

Uso ARIA o menos possível: a primeira regra do ARIA é não usar ARIA quando o HTML nativo já faz o trabalho. Quando é preciso — um combobox personalizado, um diálogo — sigo os padrões do WAI-ARIA para papéis e teclas, porque inventar é garantia de falhar em algum leitor de ecrã.

A parte automatizável está no CI: axe nos testes de componente apanha contraste, rótulos em falta e papéis errados; e a própria Testing Library força acessibilidade porque consulta por papel e nome. O que não se automatiza — a experiência real com um leitor de ecrã — faço uma vez por fluxo importante, com VoiceOver ou NVDA, porque é a única forma de descobrir que a ordem de leitura não faz sentido.

40.7 Resumo e checklist#

Nada neste capítulo é sobre um framework, e é exactamente por isso que é o que se pergunta primeiro a um full-stack: mede se o candidato percebeu que mudou de máquina, de rede e de modelo de confiança. Os dois capítulos seguintes assumem tudo o que está aqui.

  • Cinco garantias perdidas no browser — máquina, rede, thread única, confiança, estado efémero — e uma decisão por cada uma.
  • TypeScript é estrutural: formas, não nomes. A excepção é o excess property check em literais. unknown na fronteira, never para exaustividade, strict sempre.
  • Union discriminada com switch e never é o sealed mais pattern matching do Java — a ponte que vale pontos.
  • Event loop: síncrono até ao fim, depois todas as microtasks, só depois uma macrotask. await é microtask; setTimeout 0 é macrotask; ceder à UI exige macrotask; CPU a sério vai para um Worker.
  • CORS é política do browser, não protecção do servidor. Preflight em tudo o que não é «simples»; * não combina com credenciais; a mesma origem via proxy ou BFF elimina o problema.
  • Tokens: cookie HttpOnly; Secure; SameSite por omissão, BFF quando possível, memória como compromisso, storage nunca. Cookies obrigam a tratar CSRF.
  • LCP, INP, CLS no p75 de campo. LCP decompõe-se em quatro fases; INP é o event loop; CLS é espaço não reservado.
  • Cada dependência custa descarregar, analisar e compilar. Nativo primeiro, alternativa pequena depois, importação dinâmica sempre que não for crítica, orçamento no CI.
  • Testes: componentes como o utilizador (papel e nome), MSW ao nível HTTP, poucos E2E críticos, nada de detalhes de implementação. Semântica antes de ARIA; axe no CI; um leitor de ecrã por fluxo.

Checklist de preparação para as 48 horas antes da entrevista:

  • Resolver os exercícios 40.1 e 40.2 no papel antes de confirmar.
  • Dizer de cor a regra do event loop numa frase e as três consequências.
  • Explicar CORS em sessenta segundos começando por «é política do browser».
  • Ter a Tabela 40.2 na cabeça e uma defesa contra XSS e CSRF para a opção escolhida.
  • Saber os três limiares dos Core Web Vitals e a primeira suspeita de cada um.
  • Ter um exemplo real de uma dependência que recusou (ou removeu) e o que ganhou.
  • Ter a frase da Testing Library pronta, e a lista do que não testa.
